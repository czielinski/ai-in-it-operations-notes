## Data and access
Record permitted data sources, access boundaries, retention requirements and the organisation’s approval for using the selected service. Do not upload confidential operational material into an unapproved tool.

## Test set
Use permitted examples representative of normal work, difficult cases and situations where the system should abstain. Include an expected answer or assessment rubric. Keep a separate set for evaluating changes.

## Evaluation criteria
Define before testing:
- Task completion and factual correctness.
- Traceability to the underlying evidence where the task needs it.
- Handling of missing, conflicting or unauthorised information.
- Verification effort and total time compared with the current process.
- Severity of errors and their detectability by the intended user.
- Cost and performance under expected usage.

Do not treat fluent output, a citation or user satisfaction alone as proof of correctness.

## Human control and failure handling
Who checks the result? What happens when the system is unavailable or wrong? How can a user fall back to the existing process? If actions are enabled, define permissions, approval points, logging and recovery arrangements explicitly.
